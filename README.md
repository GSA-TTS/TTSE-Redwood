# ttse-redwood

Repository for the TTSE Redwood Data Agent.

This repo is the application container for the Federal Data Exchange MVP described in [003-mvp-architecture.md](https://github.com/GSA-TTS/TTSE-Redwood/blob/main/docs/adr/003-mvp-aws-infrastructure-diagram.md).

## Current scope

The repository provides a complete Day 1 sender-to-receiver transfer pipeline:

**Completed & Operational:**

- Python package using a `src/` layout
- Environment-driven agent configuration with dynamic sender/receiver agencies
- **Sender workflow**: directory scanning → policy check → compression → manifest generation → S3 upload with idempotency markers
- **Sender query mode** (Ibis adapter): validated query execution against configured source database → CSV output → S3 staging with metadata tracking
- **Receiver workflow**: S3 fetch → manifest validation → decompression with path traversal protection → target storage with idempotency markers
- **S3 integration**: Download/upload/exists operations with proper error handling
- **SFTP client integration**: Upload with exponential backoff retry, exists checks, delete operations
- Structured JSON logging and audit events with `transfer_session_id` correlation
- In-container 5-minute scheduler loop with graceful SIGTERM shutdown
- Comprehensive unit tests (375 tests, 85%+ coverage) including security hardening
- Container build with AWS S3 and SFTP integration

## Runtime model

The agent runs as a long-lived, containerized service with a 5-minute scheduler loop.

Startup behavior:
- Loads configuration from environment variables
- Initializes structured JSON logging
- Starts 5-minute scheduler loop; each cycle loads fresh config for new transfer session IDs

Per-cycle behavior:
- Scans for new transfers (sender) or landing artifacts (receiver)
- Executes sender or receiver workflow
- Logs outcome and audit events with correlation ID
- Sleeps 5 minutes before next cycle

Shutdown:
- Handles SIGTERM gracefully to support orchestration platforms (Kubernetes, ECS, etc)
- Exits current cycle and shuts down cleanly

Environment variables:

**Required for all modes:**
- `AGENT_MODE`: `sender` or `receiver`
- `AGENCY`: agency code (e.g., `dot`, `gsa`, `faa`)
- `AWS_REGION`: defaults to `us-east-1`

**Required for sender mode:**
- `SFTP_ENDPOINTS`: comma-separated SFTP endpoint(s) for receiver handoff
- `SENDER_INPUT_MODE`: sender input mode selector (`file` or `query`). Recommended default is `file`.

**Optional:**
- `TENANT`: defaults to `tts`
- `ENVIRONMENT`: defaults to `development`
- `LOG_LEVEL`: defaults to `INFO`
- `TRANSFER_SESSION_ID`: if not provided, autogenerated with timestamp + UUID
- `SFTP_USERNAME`: SFTP username injected by deployment secrets
- `SFTP_PRIVATE_KEY`: OpenSSH private key content injected by deployment secrets
- `DB_ENGINE`: database engine selector for query mode; default `postgres` (current implementation target)
- `SENDER_QUERY_INPUT_JSON`: required only when `SENDER_INPUT_MODE=query`; JSON payload with `template_id`, `params`, optional `row_limit`, and optional `timeout_seconds`
- `MAX_QUERY_ROW_LIMIT`: optional global query row cap (default: `1000000`)
- `MAX_QUERY_TIMEOUT_SECONDS`: optional global query timeout cap in seconds (default: `600`)

Mode guidance:

- Use `SENDER_INPUT_MODE=file` for the current Day 1 flow (default/fallback behavior).
- Use `SENDER_INPUT_MODE=query` when enabling sender-side SQL/query extraction via Ibis adapter.

**Query Mode (Ibis Adapter)**

When `SENDER_INPUT_MODE=query`, the sender workflow executes validated SQL queries against PostgreSQL databases:

**Workflow Steps:**

1. **Contract Validation**: Query payload is validated against allow-listed templates, required parameters, and row/timeout caps
2. **Query Execution**: Ibis builds and executes the query with timeout enforcement (signal-based SIGALRM)
3. **Output Staging**: Results are written to CSV and uploaded to S3 sender staging bucket under `query/{transfer_session_id}/` prefix
4. **Metadata Tracking**: Execution result includes row count, file size, and duration for observability
5. **Idempotency**: Successful runs write a processed marker keyed by the query fingerprint; repeated runs with the same query criteria and source DB context are skipped

**Database Connection (Query Mode):**

Query mode currently targets PostgreSQL.

The adapter connects using these environment variables:
- `DB_ENGINE` (default: `postgres`)
- `DB_HOST`
- `DB_PORT`
- `DB_NAME`
- `DB_USERNAME`
- `DB_PASSWORD`

These values are expected to be injected by your deployment's secret/configuration mechanism.

**Query Contract Structure:**

The query contract is a JSON object. Here is a sample structure (using synthetic data for implementation):

```json
{
  "template_id": "dot_contract_extract_v1",
  "params": {
    "schema": "dot",
    "table": "contract_data",
    "select_fields": ["contract_id", "piid", "vendor_name", "contract_value"],
    "filters": {
      "contract_value": {"min": 1000000},
      "award_date": {"min": "2026-01-01"}
    },
    "order_by": "award_date DESC"
  },
  "row_limit": 5000,
  "timeout_seconds": 120
}
```

**Filter Operations:**

The `filters` dict supports min/max operations for range-based filtering:
- `min`: greater-than-or-equal comparison
- `max`: less-than-or-equal comparison

Example: `{"contract_value": {"min": 1000000}}` filters to rows where contract_value >= 1000000.

**Row Limit & Timeout Enforcement:**

Default constraints (overridable via environment):
- `row_limit`: 10,000 rows per query (set via `MAX_QUERY_ROW_LIMIT` environment variable)
- `timeout_seconds`: 60 seconds per query (set via `MAX_QUERY_TIMEOUT_SECONDS` environment variable)

Two-tier cap enforcement:
- Template-specific caps defined in the query contract
- Global environment caps enforce stricter limits via min() precedence
- Example: if `MAX_QUERY_TIMEOUT_SECONDS=30` is set and contract specifies `timeout_seconds: 120`, the effective timeout is 30 seconds

**Template Allow-list Management:**

Query templates must be explicitly allow-listed before use:
- Allowed templates are defined in `src/redwood_dataagent/query_templates.py`
- Template validation enforces required parameters based on the template definition
- The allow-list is expected to be expanded or modified when onboarding additional agencies

**Error Handling & Logging:**

Query execution failures are logged with actionable error details:
- Timeout violations: logged with timeout duration and query execution time
- Configuration errors: logged with missing/invalid parameters
- Database errors: logged with connection or query syntax details
- S3 staging errors: logged with upload failure details

All outcomes are recorded in the audit trail with `EventOutcome.SUCCESS` or `EventOutcome.FAILURE`.

**Integration Notes:**

Integration with the existing sender transfer pipeline (policy check, compression, manifest generation, and transfer artifact staging) will be addressed in RED-74/RED-93.

Optional large-file transfer tuning:

- `S3_MULTIPART_THRESHOLD_MB`: multipart threshold in MB (default: `64`)
- `S3_MULTIPART_CHUNKSIZE_MB`: multipart chunk size in MB (default: `64`)
- `S3_TRANSFER_MAX_CONCURRENCY`: concurrent transfer workers (default: `8`)
- `S3_TRANSFER_DOWNLOAD_ATTEMPTS`: per-transfer download attempts (default: `5`)

## Local development

Create a virtual environment and install the package with test dependencies:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e '.[test]'
```

Or use the one-time bootstrap target:

```bash
make bootstrap
```

Run the agent:

```bash
python -m redwood_dataagent
```

Run tests:

```bash
make test
```

Run lint and coverage with Make targets:

```bash
make lint
make test-cov
```

## Local SonarQube scan before PR

This repository already contains [sonar-project.properties](sonar-project.properties), so you can run Sonar analysis locally before opening a PR.

Required environment variables:

```bash
export SONAR_TOKEN="<your-token>"
```

Note: SONAR_HOST_URL defaults to https://sonarqube-ce.prod.core.mcaas.fcs.gsa.gov/ in the Makefile, but you can override it per shell when needed.

Install scanner locally (one-time; Homebrew-based):

```bash
make sonar-setup
```

Run local Sonar scan:

```bash
make sonar-local
```

This target runs the full test coverage workflow first (`make test-cov`) so Sonar uses a fresh `coverage/coverage.xml`.

Read open maintainability issues (Sonar code smells) locally:

```bash
make sonar-maintainability
```

Single pre-PR command (lint + coverage + Sonar):

```bash
make pre-pr
```
